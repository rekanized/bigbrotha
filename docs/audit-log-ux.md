# Audit log and operator clarity — 2 October 2026

The audit log is an administrator-only activity history. It now presents an event headline, affected item, actor, execution source, local time, and recording outcome or reason before its technical data. Date groups use the configured operator timezone. Updates with up to three changed fields include a before/after preview; complete changes, metadata, identifiers, IP address, and client details remain in a native expandable section.

Quick views cover all activity, signed-in user actions, recordings, and recording failures. Search and filter controls are expandable, opening automatically when a search or additional filter is applied. Time ranges are rolling 24-hour, 7-day, and 30-day windows; all retained history remains the default. Camera, item type, actor, execution source, and event filters can be combined. Pagination preserves them. Quick-view changes clear conflicting item, actor, and event filters while retaining search, time, camera, and source constraints.

Search covers actors, current subject names and setting keys, recorded names/emails/keys, recording messages, discard reasons, and camera names. Friendly setting names such as “Google sign-in” also work. Deleted subjects can be found through stored snapshots; recordings for deleted cameras fall back to camera IDs. No historical camera name is invented when the existing audit entry lacks one.

The presenter in `app/Support/Audit/AuditLogPresenter.php` translates recording states and setting names, formats timestamps, and hides secret/password/token values in both previews and expanded changes. The page continues to escape stored text. The controller supplies validated filters and batches camera-name lookups. These presentation changes require no schema migration. Audit retention is configurable as described below.

History remains distinct from current health. A saved-recording event reports what the worker did at that time; storage and retention govern later playback availability. A discarded transient motion entry is explained as temporary cleanup rather than deletion of saved video. HTTP events with a system actor explicitly say that no signed-in user was recorded; this can happen during sign-in before authentication is established. A source of `console` is labelled “Scheduled task or command,” since the log cannot distinguish those callers.

The shared non-immersive page header now shows each screen’s description. Camera, recordings, wall-layout, and admin introductions explain operator tasks. Recording library totals are explicitly distinguished from filtered results and current storage availability. The job queue monitor links to recording failures in the audit log.

## Configurable retention — 2 October 2026

Application settings → Audit log retention accepts **1–365 days**, defaulting to **30 days** from `config/audit.php`. The admin-only `PUT /admin/settings/audit-retention` route persists `audit_retention_days` in the existing `app_settings` table. Saving it leaves the display timezone and camera recording policies unchanged. The audit page displays the active period and links back to the setting.

The existing daily `model:prune --model=App\Models\AuditLog` scheduler task now reads the saved period through `ApplicationSettingsService`. It mass-deletes entries at or before `now UTC minus retention days` in Laravel’s bounded batches. Saving does not delete history in the web request: a reduced period applies at the next daily cleanup. Increasing the period preserves more future history but cannot restore previously deleted entries. Missing settings keep the default; malformed stored values fall back to 30 days. The scheduler and its overlap protection remain in the background container.

Setting creation and changes are audited. `AppSetting` snapshots now use current raw non-secret attributes, so retention changes record the actual old/new values while avoiding decryption of the excluded SMB password. No migration or initial seed is needed.

Retention validation: **391 tests passed, 2,127 assertions** in the Docker test image; the 93 focused audit/admin tests passed again after the save-confirmation adjustment. Pint passed for all nine touched PHP files. Chromium verified settings at 1440, 390, and 320 pixels, saved 14 days through the published test site, checked the updated audit page and confirmation, and restored the 30-day default. No horizontal overflow or JavaScript errors were detected. The deployed PostgreSQL `model:prune --pretend` found no expired entries, and `schedule:list` confirmed the daily task. No deployed history was manually pruned. All four test services passed health checks; production container identities stayed unchanged.
